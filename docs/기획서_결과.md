
# 📋 [PRD] 직장인 생산성 및 시간 관리를 위한 TODO 웹앱

## 1. 개요 및 배경 (Problem & Background)

* **해결하려는 문제**: 기존의 대다수 TODO 앱은 기능이 지나치게 복잡하고 다채로워 오히려 사용자에게 피로감을 주며, 정작 오늘 반드시 처리해야 할 **핵심 업무(MIT, Most Important Task)**에 집중하지 못하게 만듭니다.
* **제품 목표**: 사용자가 업무 우선순위를 명확히 설정하고 **시간을 효과적으로 배분**할 수 있도록 지능적이고 미니멀한 시간 관리 웹앱 환경을 제공합니다.

## 4. MoSCoW 기반 핵심 기능 명세 (Feature Prioritization)

### 1) Must-have (MVP 필수 기능)
* **오늘의 MIT(Most Important Task) 3가지 지정**: 하루 최고 우선순위 과제 3개만 상단 고정.
* **빠른 할 일 등록 및 타임블록 배치**: Drag & Drop 방식으로 일일 스케줄에 할 일 배치.
* **완료 체크 및 실시간 진행률 바**: 직관적인 시각적 피드백 제공.

### 2) Should-have (차후 확장 기능)
* **집중 모드 (뽀모도로 타이머)**: 작업별 소요 시간 측정 연동.
* **주간/월간 생산성 리포트**: 몰입 시간 및 완료율 통계 시각화.

### 3) Could-have & Won't-have
* **Could-have**: Google Calendar / Slack 알림 연동.
* **Won't-have (초기 제외)**: 복잡한 다중 팀원 칸반보드 및 권한 관리.

## 5. 핵심 사용자 스토리 및 수용 조건 (Acceptance Criteria)

### 👤 User Story
> **As a** 업무 과부하를 느끼는 직장인 사용자,  
> **I want to** 오늘 반드시 끝내야 할 핵심 과제 3개를 등록하고 시간대별로 배치하고 싶다,  
> **So that** 최우선순위 업무에 먼저 집중하여 효과적으로 시간을 관리할 수 있다.

### 📑 Acceptance Criteria (Given-When-Then)
* **Given**: 사용자가 웹앱 메인 화면에 접속해 있을 때,
* **When**: 할 일을 입력하고 '오늘의 MIT 지정' 버튼을 누르면,
* **Then**: 해당 항목이 최상단 'MIT 영역(최대 3개 제한)'에 강조 등록되고, 타임라인 그리드에 drag-and-drop이 가능해진다.

**개발 시 반드시 지켜야 할 제약**

* Base UI는 합성에 `asChild`가 아니라 **`render` prop**을 씁니다 (`render={<Button variant="outline" />}`). 열림 상태도 `data-state="open"`이 아니라 **`data-open`** 입니다.
* 색 토큰을 하나 추가하려면 `globals.css`의 **세 곳**(`:root` · `.dark` · `@theme inline`)을 함께 고쳐야 합니다. 하나라도 빠지면 **빌드 에러 없이 조용히 실패**합니다.
* `src/components/ui/`는 CLI 생성물입니다. 손으로 새 파일을 만들지 말고 `npx shadcn@latest add <name>`으로 생성하세요 (`--dry-run`으로 먼저 확인).

### 7.2 아키텍처 — 별도 백엔드 서버 없음

Supabase·Express 같은 **분리된 백엔드를 두지 않습니다.** Next.js 하나로 3계층을 처리하며, 각 방식은 이미 저장소의 `/examples` 검증 화면에서 동작이 확인되어 있습니다.

| 역할 | 수단 | 참고할 검증 화면 |
| :--- | :--- | :--- |
| 데이터 읽기 | Server Component에서 DB 직접 조회 | `/examples/posts` |
| 데이터 쓰기 | Server Action + `useActionState` + `revalidatePath` | `/examples/server-actions` |
| JSON 엔드포인트(필요 시) | Route Handler (`src/app/api/`) | `/examples/route-handlers` |

**컴포넌트 경계 관례**: `page.tsx`는 전부 Server Component로 두고, 인터랙션이 필요한 조각만 `"use client"` 파일로 분리합니다. `Button`·`Badge`에 `onClick`을 달려면 그 파일이 클라이언트여야 합니다.

**인증은 두지 않습니다.** 로컬 단일 사용자 전제이므로 로그인 화면·세션·`users` 테이블을 모두 제외합니다.

### 7.3 데이터베이스 — SQLite + Drizzle ORM

로컬 전용 환경에 맞춰 **파일 기반 SQLite**를 쓰고, 접근 계층은 **Drizzle ORM**으로 둡니다.

```
npm i drizzle-orm better-sqlite3
npm i -D drizzle-kit @types/better-sqlite3
```

**선정 이유**

* **설치할 서버 프로세스가 없습니다.** DB 전체가 `data/todo.db` 파일 하나이고, Docker도 필요 없습니다 (이 머신에 Docker 미설치).
* **타입이 자동으로 따라옵니다.** TS로 쓴 스키마에서 행 타입이 추론되므로 Prisma의 `generate` 코드젠 단계나 쿼리 엔진 바이너리가 없습니다. 의존성을 최소로 유지하는 이 스타터킷의 성향과 맞습니다.
* **Next.js 설정을 건드릴 필요가 없습니다.** `better-sqlite3`는 Next 16이 **기본으로 번들링에서 제외하는 패키지 목록에 이미 포함**되어 있어 `next.config.ts`에 `serverExternalPackages`를 추가하지 않아도 됩니다. (근거: `node_modules/next/dist/docs/01-app/03-api-reference/05-config/01-next-config-js/serverExternalPackages.md`)
* **스키마 변경 이력이 파일로 남습니다.** `drizzle-kit generate`로 마이그레이션 SQL을 만들고 `drizzle-kit migrate`로 적용하며, 데이터는 `drizzle-kit studio`로 눈으로 확인합니다.

### 7.4 실행 및 검증 (배포 없음)

**이 앱은 배포하지 않습니다.** 호스팅·CI/CD·도메인·환경변수 관리는 범위 밖입니다.

| 목적 | 명령 |
| :--- | :--- |
| 개발 서버 | `npm run dev` (기본 3000) |
| 프로덕션 동작 확인 | `npm run build && npm run start` |
| 린트 | `npm run lint` · `npm run lint:fix` |
| 타입 체크 | `npx tsc --noEmit` |
| DB 마이그레이션 | `npx drizzle-kit generate` → `npx drizzle-kit migrate` |
| DB 내용 확인 | `npx drizzle-kit studio` |

작업 시 알고 있어야 할 두 가지:

* **테스트 프레임워크가 설치되어 있지 않습니다.** 테스트 러너·설정·테스트 파일이 모두 없으므로, 변경 검증은 `npm run lint` + `npx tsc --noEmit` + `npm run build`로 합니다.
* **캐시와 `revalidatePath`의 효과는 `next dev`에서 확인할 수 없습니다.** dev는 매 요청 재렌더하므로 차이가 드러나지 않습니다. `npm run build && npm run start`로 확인하세요.

### 7.5 추가 의존성 (확정)

MVP 구현에 필요한 것은 아래 하나뿐입니다. 나머지는 스타터킷에 이미 들어 있습니다.

```
npm i @dnd-kit/core @dnd-kit/sortable @dnd-kit/modifiers @dnd-kit/utilities
```

| 패키지 | 버전 | 용도 |
| :--- | :--- | :--- |
| `@dnd-kit/core` | 6.3.1 | 드래그·드롭 기본 — 할 일 목록 ↔ 타임라인 이동 |
| `@dnd-kit/sortable` | 10.0.0 | MIT 3개 순서 재배치 |
| `@dnd-kit/modifiers` | 9.0.0 | 타임라인 격자 스냅, 축 고정 |
| `@dnd-kit/utilities` | 3.x | transform → CSS 변환 헬퍼 |

**HTML5 네이티브 DnD를 쓰지 않는 이유**: §6의 비기능 요구사항인 **"단축키(Key-bindings) 중심의 빠른 입력 UX"** 와 정면으로 충돌합니다. 네이티브 `draggable` 속성은 **키보드로 드래그할 방법이 아예 없고** 터치 기기도 지원하지 않습니다. `@dnd-kit`은 `KeyboardSensor`와 스크린리더 안내를 기본 제공하므로, 이 요구사항이 선택을 사실상 결정합니다.

**React 19 호환**: `@dnd-kit/core` 6.3.1의 peer 의존성은 `react >=16.8.0`이라 이 저장소의 React 19.2.8과 충돌하지 않습니다 — `--legacy-peer-deps` 없이 설치됩니다. (`@dnd-kit/react` 0.5.0이 React 19를 명시적으로 선언하지만 아직 0.x 프리릴리스라 API가 안정적이지 않습니다. 안정판인 v6 계열을 씁니다.)

**경계 주의**: dnd-kit은 클라이언트 전용입니다. 타임라인과 MIT 목록 컴포넌트는 `"use client"` 파일이어야 하며, 이를 감싸는 `page.tsx`는 Server Component로 둡니다 (§7.2의 경계 관례).

**차트 라이브러리는 MVP 범위가 아닙니다.** 주간/월간 리포트는 Should-have이고, §9.2에서 색 토큰을 확정해 두었으므로 착수 시점에 라이브러리만 고르면 됩니다.

## 8. 데이터 모델 (로컬 SQLite)

### 8.1 파일 배치

저장소의 기존 분리 관례(`src/lib/examples/guestbook.ts` ↔ `src/app/examples/server-actions/actions.ts`)를 그대로 따릅니다.

| 경로 | 역할 |
| :--- | :--- |
| `src/db/schema.ts` | Drizzle 테이블 정의 + 행 타입 `export type` |
| `src/db/client.ts` | `better-sqlite3` 연결. dev HMR 대비 `globalThis` 싱글턴 |
| `src/lib/tasks.ts` | 조회·변환 함수, 폼 상태 타입과 초기값 |
| `src/app/actions.ts` | `'use server'` — **async 함수만** |
| `drizzle.config.ts` | drizzle-kit 설정 (스키마 경로, `data/todo.db`) |
| `data/todo.db` | DB 파일. **`.gitignore`에 추가** |

> **왜 타입과 상수를 액션 파일에 둘 수 없는가**: `'use server'` 파일은 **모든 export가 async 함수**여야 합니다. 저장소의 `guestbook.ts`가 정확히 이 이유로 분리되어 있고, 새 코드도 같은 구조를 따릅니다.

### 8.2 `tasks` 테이블 (MVP)

| 컬럼 | 타입 | NULL | 설명 |
| :--- | :--- | :---: | :--- |
| `id` | TEXT PK | N | `crypto.randomUUID()` |
| `title` | TEXT | N | 할 일 제목 |
| `notes` | TEXT | Y | 메모 |
| `planned_date` | TEXT | N | `YYYY-MM-DD`. "오늘의 MIT"를 가르는 기준 날짜 |
| `mit_order` | INTEGER | Y | `0`·`1`·`2` → MIT 항목. `NULL`이면 일반 할 일 |
| `start_min` | INTEGER | Y | 타임블록 시작(자정 기준 분). `NULL`이면 미배치 |
| `duration_min` | INTEGER | N | 소요 시간(분). 기본 30 |
| `sort_order` | INTEGER | N | 목록 내 표시 순서 |
| `done_at` | INTEGER | Y | 완료 시각(epoch ms). **`NULL` 여부가 곧 완료 상태** — 별도 boolean 컬럼을 두지 않음 |
| `created_at` | INTEGER | N | epoch ms |
| `updated_at` | INTEGER | N | epoch ms |

**MIT 최대 3개 제약**

* DB: `UNIQUE(planned_date, mit_order)` + `CHECK (mit_order IN (0, 1, 2))`
* 애플리케이션: Server Action 안에서 같은 조건을 **다시 검증**합니다. Server Action은 UI를 거치지 않은 직접 POST로도 호출될 수 있으므로 화면단 검증만으로는 부족합니다.

**SQLite 타입 매핑 주의**: SQLite에는 boolean·date 타입이 없습니다. Drizzle에서 `integer(..., { mode: "boolean" })` / `integer(..., { mode: "timestamp" })`로 매핑합니다.

### 8.3 `focus_sessions` 테이블 (Should-have 대비, MVP에서는 미생성)

뽀모도로 집중 모드와 주간/월간 리포트가 이 테이블 하나를 공유합니다.

| 컬럼 | 타입 | 설명 |
| :--- | :--- | :--- |
| `id` | TEXT PK | |
| `task_id` | TEXT FK → `tasks.id` | 어떤 할 일에 쓴 시간인지 |
| `kind` | TEXT | `focus` \| `break` |
| `started_at` / `ended_at` | INTEGER | epoch ms. `ended_at`이 `NULL`이면 진행 중 |

### 8.4 데이터 흐름 규칙

* **읽기**: Server Component가 `src/lib/tasks.ts`를 호출해 DB에 직행합니다. 클라이언트에서 `fetch`하지 않습니다.
* **쓰기**: Server Action → 서버측 검증 → DB 쓰기 → `revalidatePath("/")` → 상태 객체 반환. 예외를 throw하지 않고 **항상 상태를 반환**하는 기존 `actions.ts` 흐름을 따릅니다.
* **시간 표기**: DB에는 epoch ms로 저장하고, 화면 출력은 **`ko-KR` / `Asia/Seoul` 고정 포맷**을 씁니다 (`src/lib/examples/timing.ts`의 `formatServerTime` 참고). 로케일·타임존을 고정하지 않으면 서버와 클라이언트 렌더 결과가 달라져 하이드레이션 불일치가 납니다.
* **`Date.now()`를 컴포넌트 본문에서 호출하지 않습니다.** ESLint의 `react-hooks/purity` 규칙이 **error**로 막습니다. 모듈 스코프 함수나 Server Action 안에서만 호출하세요.
* **dev 연결 싱글턴**: `next dev`의 HMR이 모듈을 다시 평가할 때마다 새 `better-sqlite3` 연결이 생기지 않도록 `globalThis`에 캐시합니다. (개발 중 파일 락·`SQLITE_BUSY` 회피)

## 9. 디자인 기준 (DESIGN.md 적용)

시각 기준은 `docs/assets/DESIGN.md`(카카오뱅크 레퍼런스 디자인 시스템)를 따릅니다. 핵심 성격은 **흰 캔버스 · 블랙 우선 타이포 · 페일그레이 섹션 · 그림자 없음 · 큰 한글 헤딩**이며, 그 문서 스스로 밝힌 적용 우선순위(① 사용자 지시 ② 저장소 사실 ③ 시스템 계약 ④ 레퍼런스)를 그대로 지킵니다.

### 9.1 색 토큰 매핑

스타터킷의 중성 토큰을 DESIGN.md의 팔레트와 실제로 대조한 결과, **재작업이 아니라 미세 조정 수준**입니다.

| 토큰 | 현재 값 | 현재 hex | DESIGN.md | 적용 |
| :--- | :--- | :--- | :--- | :--- |
| `--background` | `oklch(1 0 0)` | `#ffffff` | `#ffffff` canvas | **변경 없음** (완전 일치) |
| `--foreground` | `oklch(0.145 0 0)` | `#0a0a0a` | `#000000` | → `oklch(0 0 0)` |
| `--primary` | `oklch(0.205 0 0)` | `#171717` | `#000000` black action | → `oklch(0 0 0)` |
| `--muted` · `--secondary` · `--accent` | `oklch(0.97 0 0)` | `#f5f5f5` | `#f7f7f7` section surface | → `oklch(0.976 0 0)` |
| `--border` · `--input` | `oklch(0.922 0 0)` | `#e5e5e5` | `#e6e6e6` divider | → `oklch(0.925 0 0)` |
| `--muted-foreground` | `oklch(0.556 0 0)` | `#737373` | `#888888` secondary | → `oklch(0.387 0 0)` (`#444444`) |

> **보조 텍스트에 `#888888`을 쓰지 않는 이유**: 흰 배경에서 대비가 **3.54:1**이라 WCAG AA 본문 기준(4.5:1)에 미달합니다. 대신 DESIGN.md가 explanatory text로 규정한 **`#444444`(9.74:1)** 를 씁니다. 같은 문서 안에서 가져온 값이면서 접근성도 통과합니다.

**다크 모드**: DESIGN.md는 흰 캔버스 기준만 기술하고 다크 값을 규정하지 않습니다. 그 문서의 Unknowns 조항("미해결 값을 그럴듯한 기본값으로 대체하지 말 것")에 따라 **`.dark`의 중성 토큰은 스타터킷 값을 그대로 둡니다.** 다크에서 새로 정의되는 것은 아래 차트 5색뿐입니다.

### 9.2 차트 색 토큰 — `chart-1` ~ `chart-5` 확정

현재 5색은 **라이트/다크 값이 완전히 동일하고 전부 무채색(chroma 0)** 이라 계열 구분이 불가능합니다. 검증을 통과한 5색으로 교체하되, **다크는 밝기를 뒤집은 값이 아니라 다크 배경용으로 따로 계단을 밟은 값**을 씁니다.

`:root` (라이트)

```css
--chart-1: oklch(0.575 0.163 255.5); /* blue    #2a78d6 */
--chart-2: oklch(0.671 0.175 40.6);  /* orange  #eb6834 */
--chart-3: oklch(0.669 0.141 162.1); /* aqua    #1baf7a */
--chart-4: oklch(0.764 0.161 75.1);  /* yellow  #eda100 */
--chart-5: oklch(0.716 0.141 357.4); /* magenta #e87ba4 */
```

`.dark`

```css
--chart-1: oklch(0.622 0.161 255.1); /* blue    #3987e5 */
--chart-2: oklch(0.622 0.173 40.1);  /* orange  #d95926 */
--chart-3: oklch(0.621 0.128 163.1); /* aqua    #199e70 */
--chart-4: oklch(0.670 0.143 73.2);  /* yellow  #c98500 */
--chart-5: oklch(0.622 0.171 0.8);   /* magenta #d55181 */
```

**검증 결과** (명도대 · 채도 하한 · 색각이상 분리도 · 배경 대비 자동 검사)

| 검사 | 라이트 | 다크 |
| :--- | :--- | :--- |
| 명도대 / 채도 하한 | PASS | PASS |
| 색각이상(CVD) 인접쌍 분리 | PASS (최저 ΔE 9.1) | PASS (최저 ΔE 8.4) |
| 정상시야 인접쌍 분리 | PASS (최저 ΔE 19.6) | PASS (최저 ΔE 19.3) |
| 배경 대비 3:1 | **WARN** — aqua · yellow · magenta | PASS |

이 검증에서 따라 나오는 **두 가지 구현 규칙**:

1. **한 차트의 계열은 3개까지.** 4번째 슬롯부터 yellow와 orange가 한 화면에 올라와 전 조합 기준을 통과하지 못합니다. 그 이상은 "기타"로 접거나 화면을 나눕니다. 리포트의 실제 계열 수(완료/미완료, 집중 시간)는 3개 이내라 제약이 되지 않습니다.
2. **라이트 모드 차트에는 직접 라벨이나 표 보기가 반드시 함께 있어야 합니다.** 3색이 배경 대비 3:1 미만이라 식별을 색에만 맡길 수 없습니다. 범례 + 값 라벨, 또는 같은 데이터의 표 토글을 함께 제공합니다.

> **유채색을 데이터에만 쓰는 이유**: DESIGN.md의 "무채색 위주, 액센트는 절제" 원칙은 **크롬(내비 · 서피스 · 버튼)** 에 적용됩니다. 데이터 계열 구분은 색이 유일하게 맡을 수 있는 역할이므로 리포트 화면에서만 유채색을 씁니다. 이 분리가 "정보에 주목하게 하라"는 DESIGN.md의 원칙과도 맞습니다.

### 9.3 타이포그래피 — Pretendard로 교체

DESIGN.md는 모든 텍스트 역할에 Pretendard Variable을 지정합니다. 이 앱은 **UI 전체가 한국어**인데 현재 폰트인 Geist에는 한글 글리프가 없어 시스템 폰트로 떨어집니다. 브랜드 일치 이전에 품질 문제라 교체합니다.

* `npm i pretendard` (1.3.9) → Variable woff2를 `src/fonts/`로 복사 → `next/font/local`로 로드
* **CSS 변수명은 반드시 `--font-sans`를 유지합니다.** `globals.css`의 `@theme inline`이 `--font-sans`를 참조하고 `@layer base`의 `html { @apply font-sans }`가 그것을 소비합니다. 이름을 바꾸면 폰트가 **조용히 적용되지 않습니다** (`src/app/layout.tsx:12`의 비표준 배선이 정확히 이 이유로 존재합니다)
* mono(`--font-geist-mono`)는 그대로 둡니다
* 한글 전체 글리프를 담아 파일이 큽니다. 로컬 전용이라 문제되지 않지만, 필요하면 dynamic subset으로 교체할 수 있습니다

**타입 스케일은 역할 비율만 차용합니다.** DESIGN.md의 90px 히어로는 기업 소개 사이트용이라 앱 화면에 쓰지 않습니다. 가져오는 것은 *큰 한글 헤딩 · 굵은 weight · 음수 자간*이라는 성격입니다.

| 역할 | 크기 / 굵기 | 근거 |
| :--- | :--- | :--- |
| 페이지 타이틀 | 32px / 700 | DESIGN.md section heading |
| 섹션 · 카드 헤딩 | 24px / 700 | DESIGN.md card heading |
| 본문 · 목록 | 16px / 400 | DESIGN.md body |
| 내비 · 보조 | 14px / 600 | DESIGN.md navigation |

### 9.4 반경과 그림자

* **반경**: DESIGN.md의 액션 반경은 **6px**입니다. `--radius`를 `0.625rem`(10px) → **`0.375rem`(6px)** 으로 낮춥니다. `rounded-lg`가 `var(--radius)`이므로 버튼이 바로 6px가 됩니다. 헤더와 탭은 각지게(`rounded-none`) 둡니다.
* **함께 고칠 것**: `--radius-xs`만 `@theme`에 없어서 `rounded-xs`(0.125rem)가 `rounded-sm`(0.375rem)보다 작은 역전이 있습니다. 이번에 `--radius-xs: calc(var(--radius) * 0.4)`를 추가해 함께 해소합니다.
* **그림자**: DESIGN.md는 그림자 없는 시스템입니다. `button.tsx`·`card.tsx`는 이미 `shadow-*`가 없고 `ring-1`로 경계를 냅니다. **앱 화면(`src/app/` 이하)에서는 `shadow-*`를 쓰지 않는다**를 규칙으로 하고, `dropdown-menu`·`popover`·`select`·`tabs` 4개 CLI 생성 파일의 기본 그림자는 **건드리지 않습니다** — 떠 있는 레이어에는 기능적 이유가 있고, `shadcn add`로 재생성할 때마다 되돌아오기 때문입니다.

### 9.5 DESIGN.md에서 의도적으로 가져오지 않는 것

| 가져오지 않는 것 | 이유 |
| :--- | :--- |
| **KakaoBank Yellow `#FFE300`** | 카카오뱅크의 보호된 브랜드 자산입니다. DESIGN.md 스스로 "이 문서는 무관한 대상 프로젝트에 대한 권한이 아니다", "브랜드 스와치에서 Yellow CTA를 유추하지 말 것"이라고 적고 있습니다. 액센트는 DESIGN.md가 실제로 관측한 **검정 액션**(`--primary` = `#000000`)을 씁니다 — "단일 액센트를 절제하고 나머지는 무채색"이라는 원칙 자체는 이쪽이 더 충실합니다. |
| 90px 히어로 타입 스케일 | 기업 소개 페이지용. 앱 화면에 맞지 않음 |
| 보조 텍스트 `#888888` | 대비 3.54:1로 WCAG AA 미달 (§9.1 참고) |
| 금융 컴포넌트 (계좌 카드 · 이체 입력 · 바텀시트 등) | DESIGN.md 자신이 "근거 없음"으로 비워 둔 영역 |

### 9.6 MIT 강조를 색 없이 처리하기

무채색 크롬 원칙을 지키면서 MIT 3개를 구분해야 하므로, DESIGN.md의 **"위계는 배치와 굵기에서 온다"** 원칙을 그대로 씁니다.

* 상단 고정 위치 + 큰 글자 + 굵은 weight
* `#f7f7f7` 섹션 서피스로 영역 구분 (카드 그림자 대신)
* 진행률 바와 완료 체크는 `--primary`(검정)
